## Phase A — ExplorerPanel Empty State Content Swap

### Goal

When no SDK context is active (the `/` route or any route without an active session directory), the ExplorerPanel shows the projects list and sessions list instead of "No workspace directory open". This is a content swap inside the existing ExplorerPanel component — no layout changes, no new top-level components.

### Rationale

Per the relocation report, the ExplorerPanel is the natural owner for projects browsing, session browsing, server management, and add-project. Currently when `tryUseSDK()` returns undefined, ExplorerPanel renders a fallback empty state. This phase replaces that fallback with the relocated Home Panel controllers.

### Files Affected

| File | Change Type | Reason |
|---|---|---|
| `packages/app/src/components/explorer-panel.tsx` | **Modify** | Replace the fallback `<EmptyState message="No workspace directory open" />` with a new sub-component that loads and renders projects + sessions |
| `packages/app/src/pages/home/home-controller.ts` | **None** (reused as-is) | Controller is already independent; ExplorerPanel imports and instantiates it |
| `packages/app/src/pages/home/home-projects-controller.tsx` | **None** (reused as-is) | Same — reused directly |
| `packages/app/src/pages/home/home-sessions-controller.tsx` | **None** (reused as-is) | Same — reused directly |
| `packages/app/src/pages/home/home-session-search-controller.ts` | **None** (reused as-is) | Same — reused directly |
| `packages/app/src/pages/home/home-scroll-controller.ts` | **None** (reused as-is) | Same — reused directly |
| `packages/app/src/pages/home/home-projects-view.tsx` | **None** | Reused as-is by ExplorerPanel |
| `packages/app/src/pages/home/home-sessions-view.tsx` | **None** | Reused as-is by ExplorerPanel |
| `packages/app/src/pages/home/home-projects.tsx` | **None** (kept for backward compat) | Wire component for Home Panel; unaffected |
| `packages/app/src/pages/home/home-sessions.tsx` | **None** (kept for backward compat) | Wire component for Home Panel; unaffected |

### Changes in Detail

**`explorer-panel.tsx`:**

1. At the top of the component (after existing imports), import the controller factory functions and view components from `pages/home/`:
   - `createHomeController`
   - `createHomeProjectsController`
   - `createHomeSessionsController`
   - `createHomeSessionSearchController`
   - `createHomeScrollController`
   - `HomeProjectsView` (for the projects sidebar)
   - `HomeSessionsView` (for the sessions list)

2. In the component body, when `activeDir()` returns undefined (no SDK context), instantiate the controllers just like `NewHome` does in `pages/home.tsx`:
   - `const home = createHomeController()`
   - `const projects = createHomeProjectsController(home)`
   - `const sessions = createHomeSessionsController(home)`
   - `const search = createHomeSessionSearchController(home, sessions)`
   - `const scroll = createHomeScrollController(sessions.data.groups)`

3. Replace the `<Show when={activeDir()} fallback={<EmptyState ... />}>` block with a new fallback that renders a **split layout**:
   - **Left column**: `<HomeProjectsView>` (the projects sidebar — uses the same props as `home-projects.tsx` wires)
   - **Right column**: `<HomeSessionsView>` (the sessions list — uses the same props as `home-sessions.tsx` wires)
   - CSS: use `flex flex-row gap-4` to match the existing Home Panel grid behavior, sized to fill ExplorerPanel width

4. When `activeDir()` is defined (session active), the existing file tree renders unchanged. No modifications to the file tree branch.

5. The ExplorerPanel `tryUseSDK()` import already exists.

**Key design constraint**: The ExplorerPanel must still render the file tree when a session is active. Only the "no SDK" empty state changes. The ExplorerPanel header (project name, refresh, close) remains unchanged.

### Controllers — Why Reused Instead of Moved

Per the "preserve existing controllers" and "smallest possible diff" principles, the controllers stay in `pages/home/` during this phase. They are already independent modules with no coupling to the `NewHome` component — `NewHome` creates and wires them, but the controllers themselves depend only on contexts (useGlobal, useTabs, useLayout, etc.) and view components. The ExplorerPanel can import and instantiate them identically.

### Dependencies

- None. Phase A has no prerequisites.

### Validation

1. **Application builds** — `bun run typecheck` passes in `packages/app`
2. **No type errors** — TypeScript compilation succeeds
3. **At `/` route**: ExplorerPanel shows projects list + sessions list (same visual as Home Panel left/right grid, but inside ExplorerPanel width)
4. **At `/server/:key/session/:id` route**: ExplorerPanel shows file tree (unchanged)
5. **Project operations work**: click project row → selection updates; add project → directory picker opens; context menu items open correct dialogs
6. **Session operations work**: click session → navigates to session; search filters sessions
7. **Server operations work**: collapse/expand, context menu, add project per server
8. **Home Panel still renders identically** at `/` (both UIs exist simultaneously — no regression)

### Rollback

- **Revert `explorer-panel.tsx`** to its previous state using `git checkout -- packages/app/src/components/explorer-panel.tsx`
- All controller files are unchanged (no move/delete)
- No other files modified
- The application returns to the previous state with zero side effects

## Phase B — ClassicMenuBar & Titlebar: Home References Removed

### Goal

Remove all references to `home.toggle` and `route.type === "home"` from the ClassicMenuBar and Titlebar. These are the only two consumer components outside the Home Panel that reference the home concept. Removing them prevents navigation to the empty `/` route after Phase C.

### Files Affected

| File | Change Type |
|---|---|
| `packages/app/src/components/classic-menu-bar.tsx` | **Modify** |
| `packages/app/src/components/titlebar.tsx` | **Modify** |

### Changes in Detail

**`classic-menu-bar.tsx`:**

1. Remove the View menu entry `{ id: "home", label: "Home", command: "home.toggle" }` at line 64.
   - Rationale: After Home Panel removal, "Home" has no destination. Per the relocation report, this is "Absolutely Forbidden" to relocate — it must be removed.
   - The View menu already contains other navigation items (Toggle Sidebar, Explorer Panel, Preview Panel, Command Palette).

**`titlebar.tsx`:**

1. Remove the `home.toggle` command registration block (currently inside the v2 titlebar `command.register("titlebar-home", ...)` at line 361-369).
   - This includes the `toggleHome` function variable and the command `{ id: "home.toggle", ... }`.
   - The `toggleHome` function is only used by this command registration. Removing both is safe.

2. Remove the three `route.type === "home"` checks scattered across the v2 titlebar:
   - Line 262: `if (route.type === "home") return` inside `matchRoute()` — this guard skips tab matching for home. After Phase C, `/` will no longer be a home route, so this guard is dead code.
   - Line 330: `if (route.type === "home")` inside the tab matching logic — same reason, dead code.
   - Line 359: `const toggleHome = () => tabs.toggleHome({ home: layout.route().type === "home", current: currentTab() })` — this is the `toggleHome` closure. Since the command is removed, this closure has no consumers.

3. For the first two guards: replace with the behavior that would handle a non-home route. Currently when route is "home", `matchRoute` returns undefined (no tab match). After removal, the route will be something else (e.g., "dir-new-session" or a new type), and `matchRoute` should return undefined for it as well (since there is no tab to match). So the guard can simply be removed — the fallthrough logic already handles the case where no tab is found.

### Dependencies

- Phase A must be complete (so ExplorerPanel handles the `/` route UX).

### Validation

1. **Application builds** — no TypeScript errors
2. **ClassicMenuBar View menu** no longer contains "Home" entry
3. **Titlebar commands** — `home.toggle` not registered (verify via `command.options`)
4. **No orphan variables** — `toggleHome` closure removed, no dangling references
5. **Tab matching** works correctly for all route types
6. **`mod+b` keybind** — no longer associated with `home.toggle` (if it was the sole registrant, keybind becomes available)

### Rollback

- Revert `classic-menu-bar.tsx` and `titlebar.tsx` with `git checkout`
- No other files affected
- Application returns to previous state

## Phase B.2 — Tabs: `toggleHome()` Redefined (parallel to Phase B)

### Goal

Change `toggleHome()` in `tabs.tsx` so it no longer navigates to `/`. After Home removal, the concept of "go home" must be replaced with "go to most recent tab" (which is already the behavior when `input.home === true`).

### Files Affected

| File | Change Type |
|---|---|
| `packages/app/src/context/tabs.tsx` | **Modify** |

### Changes in Detail

**`tabs.tsx`:**

1. Replace the `toggleHome()` function at line 364-376:
   - **Current behavior**: If `input.home` is true (already at home), navigate to the most recent tab. If a current tab exists, set recent key and navigate to `/`. Otherwise navigate to `/`.
   - **New behavior**: Remove the `navigate("/")` calls entirely. The function should simply select the most recent tab (if one exists) or be a no-op.
   - This eliminates the last consumer that navigates to `/` as "home".

2. The function signature changes from `toggleHome(input: { home: boolean; current?: Tab })` to `toggleHome(input: { current?: Tab })` or simpler — the `home` parameter is no longer needed.

3. Update the single call site in `titlebar.tsx` (line 359) to match the new signature. This is done in Phase B.

### Dependencies

- None (independent from Phase B). Can run in parallel.

### Validation

1. **Application builds** — no TypeScript errors
2. **Calling toggle** with a current tab navigates to the most recent tab (not `/`)
3. **Calling toggle** with no current tab is a no-op (does not navigate)
4. **Tab state** — `recentKey` tracking still functions correctly

### Rollback

- Revert `tabs.tsx` with `git checkout`
- Also revert `titlebar.tsx` (from Phase B) if the signature change affected it
- Application returns to previous state

## Risk Analysis

| Phase | Risk | Rationale |
|---|---|---|
| **A** | **Low** | Only adds code. No deletions. No removals. Controllers stay in place. Home Panel continues to work. Worst case: ExplorerPanel shows wrong UI — just revert one file. |
| **B** | **Low** | Removes menu entry and command registration. No behavioral change to user workflow (Home navigation was already secondary). Worst case: user misses a menu item — revert one file. |
| **B.2** | **Low** | Changes tab toggle behavior away from `/`. If toggle doesn't work, user can still click tabs directly. Worst case: revert one file. |
| **C** | **Medium** | Removes the `/` route handler and home state from LayoutProvider. Risk: `currentRoute()` fallback produces unexpected behavior for invalid paths. Risk: something still calls `layout.home.setSelection()` from ExplorerPanel (Phase A must ensure ExplorerPanel uses local state, not layout state). **Mitigation**: Verify all consumers of `layout.home.*` before removing. Search for `home.selection` and `home.setSelection` references. |
| **D** | **Medium** | Deleting 13+ files risks breaking imports if any reference was missed. **Mitigation**: Run grep for `from "@/pages/home"` and `from "./home-"` before deleting. The build will immediately catch any remaining imports. Rollback is git checkout of a directory. |
