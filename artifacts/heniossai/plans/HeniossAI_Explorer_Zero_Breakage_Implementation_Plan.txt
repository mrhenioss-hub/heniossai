========================================
1. PRINCIPLES
========================================

1.1 No Mixed Changes

Every commit contains exactly one type of change:

  infrastructure   — reorganization, hoisting, scope changes
  components       — create or modify UI components
  layout           — DOM structure / positioning changes
  css              — visual only (tokens, spacing, density)
  cleanup          — remove dead code after verification

No change set may mix types. If a change spans types, split into separate change sets.

1.2 No Hidden Refactoring

If any internal refactoring is needed (renaming, extracting a function,
simplifying), the following must be written before execution:

  - Why is it necessary?
  - What is its impact on capabilities?
  - Is there a lower-risk alternative?

Then wait for approval. Without approval = do not execute.

1.3 Cleanup Is Forbidden (Controlled Removal)

Removal of old code is permitted only after:

  1. The replacement is 100% functional
  2. All Validation Gates have passed
  3. Regression Verification has passed
  4. No remaining references or imports to the old code exist

Additionally, removal follows a mandatory workflow:

  Candidate
      |
      v
  Verification (grep for runtime references, indirect usage)
      |
      v
  Approval (recorded in Decision Log)
      |
      v
  Removal

No code may be removed solely because it appears unused.
Removal requires evidence that:
  - no runtime reference exists
  - no indirect usage exists
  - regression verification succeeds
  - approval has been recorded in the Decision Log

1.4 One Source of Truth

No code performs the same function in two places at the same time.
If a new component is created, it is used immediately and the old one is removed
(following the controlled removal workflow).

1.5 Filesystem-Based Rollback (No Git Dependency)

This project is a standalone working copy (not a Git repository).
All rollback and recovery uses filesystem backups instead of Git operations.

Before every phase:
  - A complete backup of all files that may be modified during that phase
    is created under artifacts/heniossai/backups/<phase-name>/
  - The backup is verified (files exist, readable)
  - A Restore Procedure is documented

If a phase fails:
  - Affected files are restored from the phase's Backup Point
  - Build, Typecheck, Tests, and Regression Verification are re-run
  - Only after all pass may execution continue

1.6 Evidence-Based Decisions

All implementation choices are treated as proposed solutions until validated
by implementation analysis. No implementation decision is unconditional.
Each phase identifies its key assumptions, and those assumptions must be
verified before claiming phase completion.


========================================
2. ARCHITECTURE FREEZE
========================================

2.1 Freeze Declaration

Once Phase 0 (Baseline Verification) is complete and this plan is approved,
the Explorer architecture enters a frozen state.

2.2 What Freeze Means

  - The architectural approach defined in this plan cannot change
  - Execution must follow the approved architecture
  - No architectural modifications are permitted during implementation

2.3 Unfreeze Process

If an architectural change becomes necessary:

  1. Stop implementation immediately
  2. Document the proposed change in the Decision Log
  3. Describe: what changes, why it is necessary, alternatives considered,
     impact on all phases, impact on Zero Breakage guarantees
  4. Wait for explicit approval
  5. Only after approval may implementation resume with the modified architecture

2.4 Scope of Freeze

The freeze covers:
  - Component hierarchy and responsibility boundaries
  - State management approach
  - Data flow patterns
  - Integration points with existing systems
  - Phase structure and sequencing

2.5 What Is Not Frozen

  - Implementation details (variable names, file organization within agreed structure)
  - CSS values (tokens, spacing, colors)
  - Performance optimizations that do not change architecture

4.3 Proposed Approach (Requires Validation)

This phase proposes hoisting the creation of createHomeController and its
dependent controllers from ExplorerHomeContent (which is created and destroyed
with every activeDir switch) to ExplorerPanel (which lives for the lifetime of
the sidebar).

PROPOSED CHANGE — must be validated by implementation analysis before execution:

  Before (in ExplorerHomeContent):
    function ExplorerHomeContent() {
      const home = createHomeController()
      const projects = createHomeProjectsController(home)
      const sessions = createHomeSessionsController(home)
      const search = createHomeSessionSearchController(home, sessions)
      const scroll = createHomeScrollController(sessions.data.groups)
      return ( ... )  // ProjectsView + SessionsView
    }

  After (in ExplorerPanel):
    Controllers are created at ExplorerPanel level.
    ExplorerHomeContent receives them as props instead of creating them internally.

Note: This is the currently proposed solution. The implementation analysis
must validate that this approach is correct before execution. If analysis
reveals a better approach, it must be documented in the Decision Log with
evidence and approved before proceeding.

4.4 Files Affected

  components/explorer-panel.tsx

  - ExplorerHomeContent function still exists — only its signature changes

  Risk: onCleanup for command registrations (home.palette, home.search)
  Evidence: Controllers now live longer. Cleanup only fires when ExplorerPanel
            itself unmounts, which matches the new controller lifetime.
  Status: Managed — no issue.

  Risk: createResource in home-projects-controller.tsx
  Evidence: Has no onCleanup depending on ExplorerHomeContent — safe.
  Status: Managed — no issue.

11. EMERGENCY RULES
========================================

Situation                        Action
---------                        ------
Build fails                      Stop immediately. Restore affected files from Backup Point
Typecheck fails                  Stop immediately. Restore affected files from Backup Point
Capability missing               Stop immediately. Restore affected files from Backup Point
Behavior changed unintentionally Stop immediately. Restore affected files from Backup Point
New Console Warnings             Log the cause. If unexpected -> Restore from Backup Point
Regression Verification fails    Do not proceed to next phase. Fix or Restore from Backup Point
Architecture Gate fails          Do not proceed. Stop and resolve
Phase Gate fails                 Do not proceed. Fix or Restore from Backup Point
Architecture change required     Follow Architecture Freeze unfreeze process (Section 2.3)

Restore Procedure:
  1. Copy all files from artifacts/heniossai/backups/<phase>/ to their original locations
  2. Run build, typecheck, tests, regression verification
  3. Confirm all results match Phase 0 Baseline
  4. Only after all pass may execution resume

No override is permitted for:
  - Any existing test failure
  - Any forbidden file modification
  - Forbidden import introduction
